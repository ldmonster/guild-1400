### FIXED — DemandToggle (0x465ac8) decision shape
Before: `RuleConfigDemandToggle` was wired to ride the shared `RuleEvalSettingToggle`
core (same as Service/Capacity/Supply/Threshold). The disasm shows Demand does NOT
share that shape:
- it computes only TWO trends — `base=(setting61+bias)*w63`, `high=(setting67+bias)*
  w69` — and **no mid (setting64)** trend;
- its first branch is the **inverse**: `if (base > high) *out=1` (Service uses
  `high > base`), and the lower branch fires on `high > base` (`v9 <= v10`
  negated), not `mid > base`.
Evidence: disasm 0x465ac8 — only `v10`(from [61]) and `v9`(from [67]) computed;
`if (v10 > v9) *a2=1` at 0x465b77; `if (... || v9 <= v10) return 0; *a2=0` at
0x465baf.
Fix: added a dedicated faithful `RuleEvalDemandToggle` (header + cpp) reproducing
the 2-trend inverse-branch logic, and corrected the `RuleConfigDemandToggle`
comment to state it must NOT use `RuleEvalSettingToggle`. The config's coefficients
and 0.8 multiplier were already correct (byte-verified). Added test
`AiMeisterEconomy.RuleDemandToggle`. Note: Demand was not previously wired to any
caller/test (only the config accessor existed), so this corrects latent behavior
rather than a live regression.

### Documented modeling boundaries (not divergences)
- `EvalResult::produced` gate: the binary always has eval fns (`tbl[9]`) that write
  the scores; a null eval in the binary leaves stack garbage (UB). The reimpl's
  `produced` flag is a defensive model of that always-present contract; it only
  affects the never-taken null-eval path.
- `MethodStack` capacity clamp / `Pop` empty-clamp: documented reimpl safety over
  the binary's unbounded global stack.
